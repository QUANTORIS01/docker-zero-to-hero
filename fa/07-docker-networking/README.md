# درس ۷: شبکه در Docker (Docker Networking)

## 🎯 اهداف این درس

در پایان این درس می‌توانی:

<div align='right' dir="rtl">

<span dir='rtl'>• مفهوم شبکه در Docker را توضیح بدهی.</span> <br>
<span dir='rtl'>• انواع اصلی شبکه‌های Docker را بشناسی.</span> <br>
<span dir='rtl'>• تفاوت شبکهٔ پیش‌فرض `bridge` و شبکهٔ سفارشی `bridge` را درک کنی.</span> <br>
<span dir='rtl'>• دو کانتینر را بدون انتشار پورت به میزبان به یکدیگر متصل کنی.</span> <br>
<span dir='rtl'>• از نام کانتینر برای برقراری ارتباط شبکه‌ای استفاده کنی.</span> <br>
<span dir='rtl'>• پورت‌های کانتینر را با <span dir='ltr'>`-p`</span> منتشر کنی.</span> <br>
<span dir='rtl'>• ارتباط یک کلاینت با PostgreSQL را در شبکهٔ خصوصی Docker آزمایش کنی.</span> <br>
<span dir='rtl'>• شبکه‌ها را بررسی، مدیریت و پاک‌سازی کنی.</span>

</div>

---

## ۱. شبکه در Docker چیست؟

هر کانتینر Docker یک محیط ایزوله دارد. وقتی چند کانتینر در یک پروژه داریم، ممکن است لازم باشد با یکدیگر ارتباط برقرار کنند.

برای مثال، یک برنامهٔ وب معمولاً از اجزای زیر تشکیل می‌شود:

<div align='right' dir="rtl">

<span dir='rtl'>• **Frontend:** رابط کاربری</span> <br>
<span dir='rtl'>• **Backend:** منطق برنامه و API</span> <br>
<span dir='rtl'>• **Database:** ذخیره‌سازی اطلاعات</span> <br>
<span dir='rtl'>• **Reverse Proxy:** دریافت درخواست‌ها و هدایت آن‌ها به سرویس مناسب</span>

</div>

این اجزا ممکن است در کانتینرهای جداگانه اجرا شوند.

شبکهٔ Docker امکان ارتباط بین این کانتینرها را فراهم می‌کند و به ما اجازه می‌دهد مشخص کنیم کدام کانتینرها بتوانند با یکدیگر ارتباط داشته باشند.

### یک نکتهٔ مهم

فرض کن دو کانتینر داریم:

<div align='right' dir="rtl">

<span dir='rtl'>• `web`: سرور وب</span> <br>
<span dir='rtl'>• `db`: دیتابیس</span>

</div>

اگر هر دو در یک شبکهٔ سفارشی Docker باشند، کانتینر `web` می‌تواند از طریق نام `db` به دیتابیس متصل شود.

در این حالت معمولاً نیازی نیست پورت دیتابیس را روی میزبان منتشر کنیم.

---

## ۲. انواع شبکه‌های Docker

برای مشاهدهٔ شبکه‌های موجود از دستور زیر استفاده کن:

```bash
docker network ls
```

خروجی معمولاً شامل شبکه‌هایی مانند این است:

```text
NETWORK ID     NAME      DRIVER    SCOPE
...            bridge    bridge    local
...            host      host      local
...            none      null      local
```

### ۲.۱. شبکهٔ Bridge

شبکهٔ `bridge` برای ارتباط کانتینرها در یک میزبان Docker استفاده می‌شود.

این شبکه معمولاً انتخاب مناسبی برای برنامه‌هایی است که چند کانتینر روی یک سیستم اجرا می‌کنند.

دو حالت مهم وجود دارد:

<div align='right' dir="rtl">

<span dir='rtl'>• **Default bridge:** شبکهٔ پیش‌فرضی که Docker معمولاً برای کانتینرهایی که شبکهٔ دیگری برایشان مشخص نشده استفاده می‌کند.</span> <br>
<span dir='rtl'>• **User-defined bridge:** شبکه‌ای که خودمان ایجاد می‌کنیم و کنترل بیشتری روی عضویت کانتینرها و ارتباط آن‌ها داریم.</span>

</div>

شبکهٔ سفارشی `bridge` از DNS داخلی Docker برای شناسایی کانتینرهای عضو شبکه بر اساس نام یا نام مستعار شبکه پشتیبانی می‌کند.

در مقابل، نباید فرض کنیم که کانتینرها در شبکهٔ پیش‌فرض `bridge` نیز به‌طور خودکار با نام یکدیگر قابل شناسایی هستند.

**توصیه:** برای ارتباط بین سرویس‌های یک پروژه، معمولاً از شبکهٔ سفارشی `bridge` استفاده کن.

### ۲.۲. شبکهٔ Host

در حالت `host`، کانتینر از فضای شبکهٔ میزبان استفاده می‌کند و جداسازی شبکه‌ای معمول `bridge` را ندارد.

نمونه:

```bash
docker run --rm --network host nginx:alpine
```

در این حالت رفتار پورت‌ها با حالت `bridge` و انتشار پورت با <span dir='ltr'>`-p`</span> متفاوت است؛ معمولاً برای این حالت به نگاشت پورت <span dir='ltr'>`-p`</span> نیاز نداریم.

**نکته:** پشتیبانی و رفتار شبکهٔ `host` به سیستم‌عامل و محیط Docker بستگی دارد. در Docker Desktop، این قابلیت به نسخه و تنظیمات محیط وابسته است و ممکن است با Docker Engine روی Linux یکسان نباشد.

### ۲.۳. شبکهٔ None

با شبکهٔ `none`، قابلیت شبکهٔ عادی برای کانتینر غیرفعال می‌شود و فقط رابط‌های محلی لازم مانند loopback در دسترس می‌مانند.

```bash
docker run --rm --network none alpine:3.20 ip addr
```

این حالت برای بعضی کارهای ایزوله مناسب است؛ البته به‌تنهایی جایگزین تمام سازوکارهای امنیتی نیست.

### ۲.۴. شبکهٔ Overlay

شبکهٔ `overlay` برای ارتباط شبکه‌ای بین کانتینرهایی استفاده می‌شود که روی چند میزبان Docker قرار دارند؛ معمولاً در محیط‌هایی مانند Docker Swarm.

در این درس روی شبکه‌های `bridge` تمرکز می‌کنیم؛ چون برای شروع و اجرای بسیاری از پروژه‌های محلی مناسب‌تر هستند.

---

## ۳. تفاوت Default Bridge و User-defined Bridge

این تفاوت یکی از مهم‌ترین نکات شبکه در Docker است.

<div align='center' dir="rtl">

| ویژگی | Default Bridge | User-defined Bridge |
|---|---|---|
| از قبل ایجاد شده است؟ | بله | معمولاً باید خودمان ایجاد کنیم |
| ارتباط شبکه‌ای کانتینرها | بله | بله |
| <span dir='rtl'>شناسایی خودکار کانتینرها با DNS بر اساس نام</span> | مانند شبکهٔ سفارشی نیست | بله |
| کنترل عضویت کانتینرها | محدودتر | انعطاف‌پذیرتر |
| انتخاب مناسب برای پروژه‌های چندکانتینری | معمولاً خیر | معمولاً بله |

</div>

برای ساخت شبکهٔ سفارشی:

```bash
docker network create app-network
```

حالا شبکه را بررسی کن:

```bash
docker network ls
```

برای مشاهدهٔ جزئیات شبکه:

```bash
docker network inspect app-network
```

اگر شبکه هنوز هیچ کانتینری نداشته باشد، بخش مربوط به کانتینرهای متصل خالی خواهد بود.

---

## ۴. اجرای دو کانتینر در یک شبکه

حالا یک مثال عملی اجرا می‌کنیم.

### مرحلهٔ اول: ساخت شبکه

```bash
docker network create lesson7-net
```

### مرحلهٔ دوم: اجرای یک وب‌سرور

```bash
docker run -d \
  --name web \
  --network lesson7-net \
  nginx:alpine
```

این دستور یک کانتینر Nginx ایجاد می‌کند و آن را به شبکهٔ `lesson7-net` متصل می‌کند.

در این مرحله عمداً از <span dir='ltr'>`-p`</span> استفاده نکرده‌ایم.

### مرحلهٔ سوم: آزمایش ارتباط از کانتینر دیگر

```bash
docker run --rm \
  --network lesson7-net \
  busybox:1.36 \
  wget -qO- http://web
```

اگر همه‌چیز درست باشد، خروجی HTML صفحهٔ پیش‌فرض Nginx را می‌بینی.

چه اتفاقی افتاد؟

<div align='right' dir="rtl">

<span dir='rtl'>1. کانتینر `web` در شبکهٔ `lesson7-net` اجرا شد.</span> <br>
<span dir='rtl'>2. کانتینر موقت BusyBox نیز به همان شبکه متصل شد.</span> <br>
<span dir='rtl'>3. BusyBox درخواست HTTP را به `http://web` فرستاد.</span> <br>
<span dir='rtl'>4. DNS داخلی Docker نام `web` را به آدرس مناسب در شبکه ترجمه کرد.</span> <br>
<span dir='rtl'>5. درخواست به پورت ۸۰ کانتینر Nginx رسید.</span> <br>
<span dir='rtl'>6. پاسخ HTML به ترمینال برگشت.</span>

</div>

کانتینر موقت پس از پایان دستور به‌صورت خودکار حذف می‌شود؛ چون از <span dir='ltr'>`--rm`</span> استفاده کرده‌ایم.

### نکتهٔ کلیدی

برای ارتباط بین دو کانتینر در یک شبکهٔ مناسب Docker، لازم نیست پورت مقصد را روی میزبان منتشر کنی.

در این مثال، BusyBox مستقیماً به پورت داخلی ۸۰ کانتینر `web` دسترسی پیدا کرد.

---

## ۵. تفاوت ارتباط داخلی و انتشار پورت

این دو مفهوم را با یکدیگر اشتباه نگیر.

### ارتباط داخلی

فرض کن دو کانتینر در یک شبکه هستند:

```text
Container A  ───────►  Container B:80
```

کانتینر A می‌تواند با استفاده از نام شبکه‌ای کانتینر B به پورت ۸۰ آن متصل شود.

برای این ارتباط، انتشار پورت روی میزبان لازم نیست.

### انتشار پورت

اگر بخواهیم از مرورگر یا برنامه‌ای روی میزبان به وب‌سرور دسترسی پیدا کنیم، باید پورت را منتشر کنیم:

```bash
docker run -d \
  --name web-public \
  --network lesson7-net \
  -p 127.0.0.1:8080:80 \
  nginx:alpine
```

حالا می‌توانی روی همان میزبان آدرس زیر را باز کنی:

```text
http://127.0.0.1:8080
```

ساختار دستور <span dir='ltr'>`-p`</span> به این شکل است:

```text
-p HOST_PORT:CONTAINER_PORT
```

در مثال بالا:

<div align='right' dir="rtl">

<span dir='rtl'>• `127.0.0.1`: فقط رابط loopback میزبان</span> <br>
<span dir='rtl'>• `8080`: پورت میزبان</span> <br>
<span dir='rtl'>• `80`: پورت داخل کانتینر</span>

</div>

استفاده از `127.0.0.1` باعث می‌شود پورت منتشرشده برای اتصال از طریق رابط‌های شبکهٔ دیگر میزبان در دسترس نباشد. اگر به دسترسی از سیستم‌های دیگر نیاز داری، باید آگاهانه آدرس bind و سیاست‌های فایروال را انتخاب کنی.

برای مشاهدهٔ نگاشت پورت‌ها:

```bash
docker port web-public
```

یا:

```bash
docker ps
```

**هشدار امنیتی:** انتشار پورت می‌تواند سرویس را در معرض دسترسی از میزبان یا شبکه قرار دهد. فقط پورت‌هایی را منتشر کن که واقعاً نیاز داری.

## ۶. دستور EXPOSE چه کاری انجام می‌دهد؟

ممکن است در یک Dockerfile چنین دستوری دیده باشی:

```dockerfile
EXPOSE 80
```

این دستور پورت مورد انتظار برنامه را به‌عنوان metadata تصویر مشخص می‌کند.

اما نکتهٔ مهم این است:

<div align='right' dir="rtl">

<span dir='rtl'>**`EXPOSE` به‌تنهایی پورت را روی میزبان منتشر نمی‌کند.**</span>

</div>

برای انتشار پورت هنگام اجرای کانتینر معمولاً از دستور زیر استفاده می‌کنیم:

```bash
docker run -p 8080:80 nginx:alpine
```

بنابراین:

<div align='right' dir="rtl">

<span dir='rtl'>• <span dir='ltr'>`EXPOSE 80`</span>: اعلام پورت مورد انتظار برنامه</span> <br>
<span dir='rtl'>• <span dir='ltr'>`-p 8080:80`</span>: انتشار پورت ۸۰ کانتینر روی پورت ۸۰۸۰ میزبان</span>

</div>

این دو دستور کاربردهای متفاوتی دارند.

---

## ۷. نکتهٔ بسیار مهم دربارهٔ localhost

یکی از خطاهای رایج هنگام کار با چند کانتینر، استفادهٔ نادرست از `localhost` است.

فرض کن برنامهٔ Backend در یک کانتینر و PostgreSQL در کانتینر دیگری اجرا می‌شود.

اگر از داخل کانتینر Backend این آدرس را استفاده کنی:

```text
localhost:5432
```

برنامه تلاش می‌کند به پورت ۵۴۳۲ **داخل همان کانتینر Backend** متصل شود؛ نه به کانتینر دیتابیس.

در یک شبکهٔ سفارشی Docker، آدرس معمولاً باید شامل نام کانتینر دیتابیس باشد:

```text
db:5432
```

در این مثال:

<div align='right' dir="rtl">

<span dir='rtl'>• `db`: نام کانتینر دیتابیس</span> <br>
<span dir='rtl'>• `5432`: پورت داخلی پیش‌فرض PostgreSQL</span>

</div>

به‌طور مشابه، اگر برنامه‌ای روی میزبان اجرا شود، معمولاً برای دسترسی به پورتی که منتشر شده است از آدرس میزبان مانند `127.0.0.1:5432` استفاده می‌کند.

پس آدرس اتصال به محل اجرای کلاینت بستگی دارد:

<div align='center' dir="rtl">

| محل اجرای کلاینت | آدرس نمونه |
|---|---|
| کانتینر دیگر در همان شبکه | `db:5432` |
| خود کانتینر دیتابیس | `localhost:5432` |
| برنامه روی میزبان، در صورت انتشار پورت | `127.0.0.1:5432` |

</div>

---

## ۸. پروژهٔ عملی: اتصال به PostgreSQL در شبکهٔ خصوصی

در این پروژه یک کانتینر PostgreSQL راه‌اندازی می‌کنیم و سپس از یک کانتینر موقت دیگر به آن متصل می‌شویم.

پورت دیتابیس را روی میزبان منتشر نمی‌کنیم؛ چون برای آزمایش به ارتباط داخلی شبکه نیاز داریم.

### مرحلهٔ اول: ساخت شبکه و Volume

```bash
docker network create lesson7-db-net
docker volume create lesson7-postgres-data
```

شبکه برای ارتباط بین کانتینرها و Volume برای نگهداری داده‌های دیتابیس استفاده می‌شود.

### مرحلهٔ دوم: اجرای PostgreSQL

```bash
docker run -d \
  --name db \
  --network lesson7-db-net \
  --mount source=lesson7-postgres-data,target=/var/lib/postgresql/data \
  -e POSTGRES_USER=appuser \
  -e POSTGRES_PASSWORD=local-dev-password \
  -e POSTGRES_DB=appdb \
  postgres:16
```

در این دستور:

<div align='right' dir="rtl">

<span dir='rtl'>• نام کانتینر `db` است.</span> <br>
<span dir='rtl'>• کانتینر به شبکهٔ `lesson7-db-net` متصل می‌شود.</span> <br>
<span dir='rtl'>• داده‌های PostgreSQL در Volume ذخیره می‌شوند.</span> <br>
<span dir='rtl'>• یک کاربر و دیتابیس برای تمرین ساخته می‌شود.</span> <br>
<span dir='rtl'>• هیچ پورت دیتابیسی روی میزبان منتشر نشده است.</span>

</div>

**هشدار:** رمز عبور این مثال صرفاً برای محیط آموزشی محلی است. از این رمز یا قراردادن رمزهای واقعی در تاریخچهٔ ترمینال، فایل‌های مخزن یا تنظیمات ثابت پروژه در محیط عملیاتی استفاده نکن. برای پروژه‌های واقعی، از روش مناسب مدیریت Secret استفاده کن.

### مرحلهٔ سوم: بررسی آماده بودن دیتابیس

اجرای کانتینر به معنی آماده بودن دیتابیس نیست. ممکن است چند ثانیه طول بکشد تا PostgreSQL آمادهٔ پذیرش اتصال شود.

این دستور را اجرا کن:

```bash
docker exec db pg_isready -U appuser -d appdb
```

اگر دیتابیس آماده باشد، پیامی مشابه زیر می‌بینی:

```text
/var/run/postgresql:5432 - accepting connections
```

اگر هنوز آماده نیست، چند ثانیه صبر کن و دوباره دستور را اجرا کن.

### مرحلهٔ چهارم: اتصال از کانتینر دیگر

```bash
docker run --rm -it \
  --network lesson7-db-net \
  -e PGPASSWORD=local-dev-password \
  postgres:16 \
  psql -h db -U appuser -d appdb \
  -c "SELECT current_database(), current_user;"
```

خروجی باید نام دیتابیس `appdb` و کاربر `appuser` را نشان دهد.

این آزمایش چند مفهوم را هم‌زمان ثابت می‌کند:

<div align='right' dir="rtl">

<span dir='rtl'>1. کانتینر کلاینت به همان شبکه متصل است.</span> <br>
<span dir='rtl'>2. نام `db` از طریق DNS داخلی Docker شناسایی می‌شود.</span> <br>
<span dir='rtl'>3. PostgreSQL از پورت داخلی ۵۴۳۲ استفاده می‌کند.</span> <br>
<span dir='rtl'>4. برای اتصال بین کانتینرها، انتشار پورت دیتابیس روی میزبان ضروری نیست.</span>

</div>

متغیر `PGPASSWORD` در این مثال صرفاً برای ساده‌سازی تمرین استفاده شده است. برای محیط عملیاتی، از سازوکار مدیریت Secret مناسب استفاده کن.

### مرحلهٔ پنجم: بررسی شبکه

```bash
docker network inspect lesson7-db-net
```

در خروجی، کانتینرهای متصل به شبکه را مشاهده کن.

### مرحلهٔ ششم: بررسی لاگ دیتابیس

```bash
docker logs db
```

برای دنبال کردن لاگ‌ها به‌صورت زنده:

```bash
docker logs -f db
```

برای خروج از حالت دنبال کردن لاگ‌ها، `Ctrl+C` را فشار بده. این کار معمولاً کانتینر را متوقف نمی‌کند.

## ۹. مدیریت شبکه‌ها

در این بخش با دستورهای پرکاربرد آشنا می‌شویم.

### مشاهدهٔ شبکه‌ها

```bash
docker network ls
```

### مشاهدهٔ جزئیات شبکه

```bash
docker network inspect lesson7-net
```

### ایجاد شبکه

```bash
docker network create my-network
```

### اتصال یک کانتینر موجود به شبکه

```bash
docker network connect my-network web
```

کانتینر باید وجود داشته باشد و در وضعیت مناسبی برای اتصال شبکه‌ای قرار داشته باشد.

### جدا کردن کانتینر از شبکه

```bash
docker network disconnect my-network web
```

### حذف شبکه

```bash
docker network rm my-network
```

معمولاً نمی‌توان شبکه‌ای را که هنوز کانتینرهایی به آن متصل هستند حذف کرد. ابتدا کانتینرها را از شبکه جدا کن یا آن‌ها را حذف کن.

### پاک‌سازی شبکه‌های بلااستفاده

```bash
docker network prune
```

این دستور شبکه‌های سفارشیِ بلااستفاده را حذف می‌کند. پیش از تأیید، فهرست مواردی را که قرار است حذف شوند بررسی کن.

**نکته:** `docker network prune` برای پاک‌سازی شبکه‌ها است؛ Volumeها را پاک نمی‌کند.

---

## ۱۰. اتصال و جداسازی شبکه در زمان اجرا

گاهی کانتینر از قبل اجرا شده است و می‌خواهیم آن را به شبکه‌ای دیگر متصل کنیم.

برای مثال:

```bash
docker network create monitoring-net
docker network connect monitoring-net web
```

حالا کانتینر `web` به دو شبکه متصل است.

برای بررسی:

```bash
docker inspect web
```

در خروجی، بخش `NetworkSettings` را پیدا کن.

اگر می‌خواهی شبکهٔ دوم را جدا کنی:

```bash
docker network disconnect monitoring-net web
```

این روش برای آزمایش و مدیریت شبکه مفید است؛ اما در پروژه‌های واقعی بهتر است ساختار شبکه‌ها و اتصال سرویس‌ها را به‌صورت قابل تکرار تعریف کنی. در درس Docker Compose خواهیم دید که چطور این کار را ساده‌تر انجام دهیم.

---

## ۱۱. عیب‌یابی مشکلات رایج شبکه

### مشکل اول: کانتینرها یکدیگر را پیدا نمی‌کنند

دلایل احتمالی:

<div align='right' dir="rtl">

<span dir='rtl'>• کانتینرها در شبکه‌های متفاوت هستند.</span> <br>
<span dir='rtl'>• از نام اشتباهی برای مقصد استفاده شده است.</span> <br>
<span dir='rtl'>• شبکه از نوع `bridge` پیش‌فرض است و انتظار DNS مبتنی بر نام کانتینر داریم.</span> <br>
<span dir='rtl'>• کانتینر مقصد اجرا نمی‌شود یا برنامه داخل آن آماده نیست.</span>

</div>

بررسی کن:

```bash
docker network ls
docker network inspect lesson7-net
docker ps
```

### مشکل دوم: استفاده از localhost برای اتصال به دیتابیس

اگر Backend و دیتابیس در دو کانتینر جداگانه باشند، `localhost` معمولاً آدرس اشتباهی است.

به‌جای آن از نام کانتینر دیتابیس در شبکهٔ سفارشی استفاده کن؛ برای مثال:

```text
db:5432
```

### مشکل سوم: اتصال از میزبان برقرار نمی‌شود

اگر می‌خواهی از مرورگر یا برنامهٔ روی میزبان به کانتینر متصل شوی، بررسی کن آیا پورت منتشر شده است یا نه:

```bash
docker ps
docker port web-public
```

اگر پورت منتشر نشده باشد، ممکن است دسترسی مستقیم از میزبان برقرار نشود؛ حتی اگر ارتباط داخلی کانتینرها به‌درستی کار کند.

### مشکل چهارم: دیتابیس هنوز آماده نیست

کانتینر ممکن است در حال اجرا باشد، ولی سرویس داخل آن هنوز آمادهٔ پذیرش اتصال نباشد.

برای PostgreSQL:

```bash
docker exec db pg_isready -U appuser -d appdb
```

در برنامهٔ واقعی نیز بهتر است اتصال به دیتابیس و راه‌اندازی سرویس‌ها در برابر تأخیرهای موقت مقاوم باشد.

### مشکل پنجم: پورت در دسترس نیست

موارد زیر را بررسی کن:

<div align='right' dir="rtl">

<span dir='rtl'>• آیا برنامه واقعاً روی پورت مورد انتظار گوش می‌دهد؟</span> <br>
<span dir='rtl'>• آیا پورت صحیح را در دستور <span dir='ltr'>`-p`</span> مشخص کرده‌ای؟</span> <br>
<span dir='rtl'>• آیا پورت میزبان قبلاً توسط برنامهٔ دیگری اشغال شده است؟</span> <br>
<span dir='rtl'>• آیا محدودیت فایروال یا تنظیمات سیستم‌عامل مانع اتصال شده است؟</span>

</div>

## ۱۲. تمرین‌های درس

### تمرین ۱: ساخت شبکه

یک شبکه به نام `practice-net` بساز و با دستورهای Docker بررسی‌اش کن.

**هدف:** یادگیری ایجاد و بررسی شبکه.

### تمرین ۲: ارتباط دو کانتینر

یک کانتینر Nginx به نام `practice-web` در شبکهٔ `practice-net` اجرا کن.

سپس با یک کانتینر BusyBox بررسی کن که صفحهٔ Nginx از طریق نام `practice-web` قابل دریافت باشد.

راهنمای دستور دوم:

```bash
docker run --rm \
  --network practice-net \
  busybox:1.36 \
  wget -qO- http://practice-web
```

**هدف:** درک DNS داخلی Docker و ارتباط کانتینرها.

### تمرین ۳: انتشار پورت

یک کانتینر Nginx دیگر اجرا کن و پورت آن را روی پورت `8081` میزبان منتشر کن. در صورت استفادهٔ محلی، ترجیحاً آن را به `127.0.0.1` محدود کن.

**هدف:** تفاوت ارتباط داخلی و انتشار پورت را در عمل ببینی.

### تمرین ۴: بررسی DNS

دو کانتینر را به یک شبکهٔ سفارشی متصل کن. سپس از داخل یکی از آن‌ها با نام کانتینر دیگر درخواست HTTP بفرست.

**هدف:** درک اینکه چرا نام کانتینر در شبکهٔ سفارشی قابل استفاده است.

## ۱۳. چالش نهایی درس

یک محیط آزمایشی بساز که شرایط زیر را داشته باشد:

<div align='right' dir="rtl">

<span dir='rtl'>1. شبکه‌ای به نام `final-network` داشته باشد.</span> <br>
<span dir='rtl'>2. یک کانتینر Nginx به نام `frontend` اجرا شود.</span> <br>
<span dir='rtl'>3. یک کانتینر PostgreSQL به نام `database` اجرا شود.</span> <br>
<span dir='rtl'>4. داده‌های PostgreSQL در یک Volume ذخیره شوند.</span> <br>
<span dir='rtl'>5. هر دو کانتینر به شبکهٔ `final-network` متصل باشند.</span> <br>
<span dir='rtl'>6. پورت دیتابیس روی میزبان منتشر نشود.</span> <br>
<span dir='rtl'>7. بتوانی از یک کانتینر موقت به دیتابیس متصل شوی و نام دیتابیس و کاربر را بررسی کنی.</span> <br>
<span dir='rtl'>8. بتوانی با دستور `docker network inspect` اتصال کانتینرها به شبکه را بررسی کنی.</span>

</div>

### معیارهای موفقیت

<p dir='rtl'>
• ارتباط داخلی بر اساس نام کانتینر برقرار باشد. <br>
• برای ارتباط داخلی، پورت دیتابیس روی میزبان منتشر نشده باشد. <br>
• داده‌های دیتابیس در Volume نگهداری شوند. <br>
• بتوانی تفاوت شبکه، Volume و انتشار پورت را توضیح بدهی.
</p>

## ۱۴. پاک‌سازی محیط تمرین

پس از پایان تمرین، منابعی را که ایجاد کرده‌ای حذف کن.

ابتدا کانتینرهای مربوط به مثال‌ها را متوقف و حذف کن:

```bash
docker rm -f web web-public db
```

اگر بعضی از این کانتینرها وجود نداشته باشند، Docker برای همان نام‌ها پیام خطا می‌دهد. در این صورت فقط نام‌های موجود را حذف کن.

شبکه‌ها را حذف کن:

```bash
docker network rm lesson7-net lesson7-db-net
```

<p dir='rtl'>
Volume دیتابیس را فقط زمانی حذف کن که مطمئن هستی دیگر به داده‌های آن نیاز نداری:
</p>

```bash
docker volume rm lesson7-postgres-data
```

**هشدار:** حذف Volume می‌تواند داده‌های ذخیره‌شدهٔ دیتابیس را از بین ببرد. حذف کانتینر به‌تنهایی لزوماً Volume را حذف نمی‌کند.

## ۱۵. جمع‌بندی

در این درس یاد گرفتی:

<div align='right' dir="rtl">

<span dir='rtl'>• شبکهٔ Docker ارتباط بین کانتینرها را فراهم می‌کند.</span> <br>
<span dir='rtl'>• شبکهٔ سفارشی `bridge` برای بسیاری از پروژه‌های چندکانتینری محلی مناسب است.</span> <br>
<span dir='rtl'>• DNS داخلی شبکهٔ سفارشی اجازه می‌دهد کانتینرها با نام یکدیگر ارتباط برقرار کنند.</span> <br>
<span dir='rtl'>• `localhost` داخل کانتینر به همان کانتینر اشاره می‌کند.</span> <br>
<span dir='rtl'>• برای ارتباط داخلی کانتینرها معمولاً نیازی به انتشار پورت روی میزبان نیست.</span> <br>
<span dir='rtl'>• `-p` برای انتشار پورت کانتینر روی میزبان استفاده می‌شود.</span> <br>
<span dir='rtl'>• `EXPOSE` به‌تنهایی پورت را منتشر نمی‌کند.</span> <br>
<span dir='rtl'>• شبکه‌ها و Volumeها دو مفهوم متفاوت با مسئولیت‌های متفاوت هستند.</span>

</div>

**اصل طلایی:** فقط پورت‌هایی را روی میزبان منتشر کن که واقعاً به دسترسی از میزبان نیاز دارند. برای ارتباط داخلی بین سرویس‌ها، شبکهٔ مناسب Docker و نام سرویس یا کانتینر را به کار ببر.

در درس بعدی سراغ Docker Compose می‌رویم تا چند سرویس، شبکه و Volume را با یک فایل قابل تکرار مدیریت کنیم.
